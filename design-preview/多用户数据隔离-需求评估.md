## 一、结论速览

| 问题 | 结论 |
| --- | --- |
| 现有数据库能否**直接**实现？ | **不能。** 缺两个必需字段：`stock_master` 无归属字段、`users` 无角色字段 |
| 能否**改到**满足？ | **能。** 纯加法改造：加 2 列 + 索引 + 调整 1 个唯一键，**不重建库、不丢数据**，表量级小（订单百级），`ALTER` 秒级完成 |
| 主要工作量在哪？ | **不在数据库，在代码**：全项目所有 `stock_master` 读写点都没有用户维度，需逐一加作用域（约 16 处调用点，见 §4） |
| 有没有必须产品先拍板的点？ | **有 1 个阻塞项**：同一只股票（如 `SZ002027`）能否被多个用户各自持有一条？三种方案成本差异很大，见 §3.2 |
| 风险等级 | 中。越权漏改会导致「能看到 / 能改别人的数据」，属安全类缺陷（P0），必须集中收敛到**一处**判定，不允许各视图各写各的 |

## 二、现状盘点（事实，非推测）

### 2.1 数据库：两个必需的字段都不存在

| 检查项 | 现状 | 是否满足需求 |
| --- | --- | --- |
| `stock_master` 有无归属用户列 | **无**。`database.py:50-65` 的 `stock_master` 只有 `stock_name / stock_code / target_pettm / ... / status`，没有任何 `user_id` | ❌ 无法表达「这条订单是谁的」 |
| `users` 有无角色列 | **无**。`database.py:18-33` 的 `users` 只有 `username / password_hash / email / phone / bench_code / last_login / updated_at / created_at` | ❌ 无法表达「谁是 admin」 |
| `stock_code` 唯一性 | **全局唯一**（`stock_code VARCHAR(20) NOT NULL UNIQUE`，`database.py:54`） | ⚠️ 直接后果：即便加了 `user_id`，两个人也**不能**各加一条 `SZ002027`。必须先决策 §3.2 |
| 子表是否可继承归属 | 可以。`stock_warehouse / stock_pe / stock_pb / stock_alarm / stock_kline / stock_indicator / stock_indicator_config / stock_ai_report` 全部以 `stock_master_id` 关联且 `ON DELETE CASCADE` | ✅ 只要 `stock_master` 有归属，下游天然继承，**不需要逐表加列** |
| 与「无权限体系」的历史约定 | `spec/current/001-user-auth.md` §5 已写明：`admin_required` / `permission_required` 因依赖不存在的 `role` 字段被当作死代码删除，并注明「如需权限管理须另立变更：先加字段、再补装饰器」 | ✅ 本次正好是这条约定的落地 |

### 2.2 代码：所有查询都没有用户维度

`views/stock_orders.py` 与 `views/ai_analysis.py` 的每个路由都只校验「登录了没」（`@login_required`），**从不校验「这条数据是不是你的」**。

已知绕过方式（评估阶段已确认存在，暂未修）：

- 直接改 URL `/stock/edit/3`、`/stock/delete/3`、`POST /stock/toggle_status/3` → 可编辑/删除/暂停任意订单；
- `?stock_id=3` 拼到 `/stock/alarm_settings`、`/stock/ai/` → 可看别人订单的阈值与 AI 报告；
- `POST /stock/refresh_quotes` 传任意 `ids` → 可批量拉取别人订单的行情；
- `GET /stock/api/kline/3` → 可拉别人订单的 K 线。

### 2.3 「全局生效账户」口径与新需求冲突（需一并决策）

`models/account_settings.py` 明确写着「本系统是**单账户运维视角**，全局设置以**最近保存过的账户**为准（`ORDER BY updated_at DESC, id ASC`）」，并以此决定：

- 基准指数 `resolve_bench_code()`（`account_settings.py:150`）
- 告警收件人 `resolve_alarm_recipients()`（`account_settings.py:166`）
- 通知开关 `notify_enabled()`（`account_settings.py:192`）

引入多用户后这个「最近保存者即全局」的口径会变得不可预期：**A 保存一下设置，B 的告警邮件就改投给 A**。这是本次必须一并处理或显式声明「暂不处理」的点，见 §3.5 与 §7-Q3。

## 三、需求改写（原文 3 条 → 可实现的 8 条）

原文：

1. 不同用户登录后只能看到自己名下所有的股票，其他用户的看不到。
2. 只有 admin 管理员账号能看到所有的股票。
3. 现有的数据库是否能实现这个需求，如果不满足是否可以更改到满足。

第 3 条已在 §1/§2 回答。前 2 条改写如下。

### 3.1 R1 数据归属（新增约定）

1. `stock_master` 每一行**有且仅有一个归属用户**（新增 `user_id`，外键 `users(id)`）。
2. 新建订单时 `user_id` = 当前登录用户，**不接受客户端传值**（同 `toggle_status` 的既有做法：目标值由服务端定）。
3. `user_id` 写入后**不可通过表单修改**（没有「转让订单」入口）。
4. 删除用户时**不允许**级联删订单，用 `ON DELETE RESTRICT`（当前系统无删除用户入口，避免误删清掉历史行情与告警）。

### 3.2 R2 同一只股票能否被多人各自持有 —— **阻塞项，需产品拍板**

现状 `stock_code` 全局唯一，加归属后必须选一个：

| 方案 | 做法 | 优点 | 代价 / 风险 | 评估 |
| --- | --- | --- | --- | --- |
| **A（推荐）** 按人唯一 | 唯一键改 `UNIQUE KEY uk_user_code (user_id, stock_code)`，`stock_code` 不再全局唯一 | 语义最直白：每人独立阈值、独立告警、独立 K 线；改动面最小 | 同一代码被 N 人持有 → 监控线程每轮对同一代码打 **N 次**雪球请求、K 线重复落 N 份。**必须在监控侧按 `stock_code` 去重**（一轮内同代码只取一次行情，回写全部同代码订单），否则外部请求量随用户数线性增长 | ✅ 推荐，但**去重是强制配套项** |
| B 共享标的 | `stock_code` 保持全局唯一，另建 `stock_watch(user_id, stock_master_id)` 关联表，多人共享同一条订单 | 行情 / K 线 / 指标只采一份，不浪费外部请求 | 阈值、告警、PE/PB 备注是**共享**的，A 改阈值 B 跟着变，与「自己名下」直觉冲突；几乎每个查询都要多一层 JOIN，改动面最大 | ⚠️ 仅在「阈值也必须共用」时选 |
| C 独占 | `stock_code` 保持全局唯一 + 单一 owner；第二个人添加同代码时提示「该标的已被占用」 | 最省事，零去重成本 | 多人想盯同一只票时直接不可用；「被谁占用」要不要暴露给用户也是个隐私问题 | ❌ 不推荐 |

**默认按方案 A 推进**，除非产品明确选 B 或 C。

### 3.3 R3 可见性规则（需求 1 的正式表述）

| 角色 | 可见范围 |
| --- | --- |
| 普通用户（`role='user'`） | 仅 `user_id = 自己` 的订单，及其衍生的告警 / 阈值 / K 线 / 指标快照 / AI 报告 |
| 管理员（`role='admin'`） | 全部订单（`spec/current/` 002 中「订单不区分用户」的限制随之作废） |

作用域必须覆盖**每一处**读：

| 页面 / 接口 | 现在 | 改造后 |
| --- | --- | --- |
| `GET /stock/list` | 全量 | 按归属过滤；页头统计 `total / active / inactive / alarm_active` 同口径过滤 |
| `GET /stock/indicator` | 全量 | 同上 |
| `GET /stock/alarm_settings`（列表与 `?stock_id=` 单条） | 全量 | 同上 |
| `GET /stock/recent_alarms` | 全量 | 告警按归属用户的订单过滤；`StockAlarm.get_stats()` 同样过滤 |
| `GET /stock/api/kline/<id>` | 无校验 | 校验归属，否则 403 |
| `POST /stock/refresh_quotes` | 传啥 id 查啥 | 只返回归属自己的 id（非归属 id 静默丢弃） |
| `GET /stock/ai/` 与 `/stock/ai/api/search` | 全量 | 同上（搜索结果、报告历史、最近分析只看自己的） |
| 侧栏「指标监控」徽标（`app.py:74`） | 全库计数 | 按归属过滤 |

### 3.4 R4 越权防护（需求 1 隐含，但原文没写，必须补）

1. `edit / delete / toggle_status / alarm_settings 保存 / ai 的 analyze 与 ask`：先取行、再校验归属，**不匹配一律 403（或 flash + 回列表）**，并在日志记 `logger.warning('越权访问')`（`app.py:110` 已有 403 处理器可直接复用）。
2. 判定**只允许有一个实现**：新增 `utils/access.py` 统一提供 `is_admin()` / `owned_stock_or_403(id)` / `scope_params()`，各视图只调用、不自己写 `WHERE user_id =`。理由同 `models/account_settings.py` 头部注释——「页面写 A、邮件发到 B」这类漂移最难排查。
3. `session` 里写入 `role`（登录时），避免每次请求查 `users` 表；管理员权限变更需重新登录才生效（可接受，写入规格）。

### 3.5 R5 管理员认定（需求 2 的落地方式）

推荐组合：

1. `users` 增 `role ENUM('user','admin') NOT NULL DEFAULT 'user'`；
2. **存量库**：把 `id` 最小的用户置为 `admin`（保证改造后立刻有一个管理员，不会把自己锁在外面）；
3. **新用户**：默认 `user`；提供 `flask set-admin <username>` CLI 提升（无新凭据，符合安全红线）；
4. 可选增强：环境变量 `ADMIN_USERNAMES`（逗号分隔用户名，非凭据）在登录时同步 `role`，便于自动化部署。

> 反例（不采纳）：用用户名硬编码 `if username == 'admin'` —— 与「明文凭据/硬编码」红线同类，且不可扩展。

### 3.6 R6 存量数据回填

1. 加列时允许 `NULL` → 回填 → 再改 `NOT NULL`；
2. 回填规则：全部存量订单归到被认定为 admin 的那个用户（§3.5-2）；
3. 回填脚本幂等（只处理 `user_id IS NULL`），可重复执行；执行前**必须先备份**。

### 3.7 R7 明确不在本次范围内（避免范围蔓延）

以下三项当前是「全局共享」，本次**建议保持不变**，但在规格里显式声明：

- `stock_ai_config`（AI 温度 / 月度上限 / 数据范围）仍是单行全局表；
- `stock_indicator_config` 的「留空继承全局」语义不变；
- 注册仍开放（任何人可自助注册，注册后是空列表）。

若产品要求改成「按用户」，需另立变更（见 §7-Q4/Q5）。

### 3.8 R8 后台监控的影响（必须同步改，否则功能退化）

1. `models/stock_monitor.py:822` `StockMaster.get_active_stocks()` **不加**用户过滤——它必须监控所有人的订单，这点不变；
2. 若采用方案 A，**新增同 `stock_code` 去重**：一轮内同一代码只请求一次行情、只采一次 K 线，结果回写给所有持有该代码的订单；
3. 告警收件人：现状 `resolve_alarm_recipients()` 取「最近保存账户」的邮箱（§2.3）。多用户下应改为「**订单归属用户的邮箱 + 该用户的通知开关**」。这一条是否纳入本次，需产品决策（§7-Q3）。

## 四、数据库改造方案（DDL 草案）

全部走 `database.py` 的幂等迁移机制：`_COLUMN_MIGRATIONS`（`database.py:269`）+ `_INDEX_MIGRATIONS`（`database.py:258`）+ `CREATE TABLE IF NOT EXISTS`（`database.py:50`）。**新增 DDL 不得只写在 CREATE TABLE 里**，否则存量库不会生效。

```sql
-- 步骤 1：users 增角色（幂等，先查 information_schema.COLUMNS 再执行）
ALTER TABLE users
  ADD COLUMN role ENUM('user','admin') NOT NULL DEFAULT 'user';

-- 步骤 2：stock_master 增归属（先可空，回填后再收紧）
ALTER TABLE stock_master
  ADD COLUMN user_id INT NULL,
  ADD INDEX idx_stock_owner (user_id);
ALTER TABLE stock_master
  ADD CONSTRAINT fk_stock_master_user
  FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE RESTRICT;

-- 步骤 3：存量回填（幂等：只处理 user_id IS NULL）
UPDATE stock_master SET user_id = (SELECT id FROM users ORDER BY id ASC LIMIT 1)
WHERE user_id IS NULL;

-- 步骤 4：唯一键调整（仅方案 A；必须先确认 R2 选型）
ALTER TABLE stock_master DROP INDEX stock_code;
ALTER TABLE stock_master ADD UNIQUE KEY uk_user_code (user_id, stock_code);

-- 步骤 5：回填完成后收紧（可放到下一次迁移执行）
ALTER TABLE stock_master MODIFY user_id INT NOT NULL;
```

同步登记：`spec/PROJECT_WIKI.md` 的数据字典（守则 §2 要求）。

**回退方案**：`user_id` 列与索引可 `DROP`；`uk_user_code` 可 `DROP` 后重建 `UNIQUE(stock_code)`（若回填后出现同代码多行，重建会失败 → 回退前需先人工去重）。评估期不执行。

## 六、验收条件（可测，将写入变更记录）

1. 用户 A 登录，`/stock/list` 只出现 `user_id=A` 的订单；页头 `total / active / inactive / 触发告警` 与可见行一致。
2. A 直接访问 `/stock/edit/<B 的订单 id>`、`POST /stock/delete/<B 的 id>`、`POST /stock/toggle_status/<B 的 id>` → 均被拦截（403 或 flash 回列表），库中数据不变。
3. `POST /stock/refresh_quotes` 传 `{"ids":[B 的 id]}` → 返回空 quotes，不泄露行情。
4. `GET /stock/api/kline/<B 的 id>` → 403。
5. `/stock/ai/?stock_id=<B 的 id>` → 不展示 B 的报告；`/stock/ai/api/search?q=<B 独有代码>` → 返回 0 条。
6. admin 登录 → 上述页面均为全量口径；普通用户的可见集是 admin 可见集的真子集。
7. 同一 `stock_code`：按方案 A 时，A、B 各持有 `SZ002027` 能各自保存、各自改阈值、互不影响；监控一轮内对该代码**只发一次**雪球行情请求（用日志/计数验证）。
8. `stock_code` 冲突提示：A 名下已有 `SZ002027` 时，A 再创建同代码 → 仍报「已存在」（唯一键 `(user_id, stock_code)` 生效）。
9. 存量回填：执行迁移后 `SELECT COUNT(*) FROM stock_master WHERE user_id IS NULL` = 0；回填脚本二次执行无副作用。
10. A 删除自己的订单 → 其 K 线 / 告警 / 指标 / AI 报告一并消失（现有 CASCADE 行为不变）。
