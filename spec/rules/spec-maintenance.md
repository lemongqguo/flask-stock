# 规格与进度维护规范

> 本文件规定 `spec/` 怎么写、放哪里、一次变更如何闭环，以及规格与 [`../PROGRESS.md`](../PROGRESS.md) 如何同步。

---

## 1. 目录与命名（硬性）

```
spec/
├── README.md        索引入口（唯一入口，必须最新）
├── PROGRESS.md      开发进度台账
├── Spec.md          方法论（只读）
├── PROJECT_WIKI.md  项目百科（部署/配置/使用）
├── rules/           持续规则（本目录）
├── current/         当前有效规格  NNN-slug.md
├── changes/         变更记录      NNN-slug/change.md
├── decisions/       决策记录      NNN-slug.md
├── plans/           计划与路线图
└── archive/         归档          current/  changes/
```

- **文件名**：`NNN-slug.md`，`NNN` 三位递增（`001` 起），slug 小写英文连字符（如 `006-alarm-cooldown`）。
- **编号只增不复用、不删除**；废弃文件移入 `archive/` 后编号不再分配。
- **不得新增同级目录**；新内容必须归入上述分组之一。
- 目录名固定为英文小写：`rules / current / changes / decisions / plans / archive`。

## 2. 一份 `current/` 规格必须包含的内容

按顺序写，缺项要写明"不适用"及原因：

1. **头部元信息**：状态（已实现 / 部分实现 / 未开始）、最后更新日期、实现位置、相关待办链接。
2. **场景**：谁在什么情况下用，解决什么问题。禁止出现"更好""更热"这类无法验收的词。
3. **术语**：本规格涉及的关键概念与字段含义。
4. **当前有效行为**：分条描述系统**现在**的真实行为，精确到判定条件与阈值；关键逻辑贴代码片段。
5. **验收条件**：可执行的判定语句（给定输入 → 期望输出），每条都能实际验证。
6. **已知限制**：当前确认但未处理的问题，链接到 `PROGRESS.md` 的缺陷编号。

写作要求：
- 写"是什么"，不写"怎么实现"；实现细节留给代码与 `PROJECT_WIKI.md`。
- 阈值、边界、错误表现必须给出具体值（如"±3%"而不是"略有偏离"）。
- 状态为"未开始"的规格，验收条件即未来的开发任务清单。

## 3. 一次变更的闭环流程

```
发现问题
  └─> 判断类型：实现不符原约定？/ 产品要改行为？/ 纯重构？/ 新能力？
        ├─ 实现不符  → 依据现有 current/ 规格补回归测试 → 修复
        └─ 行为变更  → 先改 changes/ 中的约定 → 再调整测试期望 → 实施
  └─> 实施代码
  └─> 按"验证范围"实际验证，记录结果（含未验证范围）
  └─> 合入：把差异写入 current/ 对应规格
  └─> 同步：更新 PROGRESS.md 与 README.md
  └─> 归档：changes/NNN-slug/ 移入 archive/changes/
```

**关键判断（Spec.md 1.3）**：先确认问题是"实现没满足约定"还是"约定本身要变"，两者的处理方式不同——
前者不该改规格，后者必须先改约定。

## 4. 规格与进度的同步规则

1. **改规格必改进度**：`current/` 任一文件变动 → 更新 `PROGRESS.md` 中对应模块状态、台账条目与"最后更新"日期。
2. **改进度必指规格**：`PROGRESS.md` 每条模块/缺陷必须有 `../current/NNN-*.md` 链接；尚无规格的模块先补规格再开发。
3. **缺陷闭环**：缺陷从 `待办` → `已验证` 时，同步更新对应规格的"已知限制"章节（移除已修复项、补新增项）。
4. **状态定义统一**：
   - 模块：`已实现` / `部分实现` / `未开始`
   - 缺陷：`待办` / `进行中` / `已验证` / `已合入`
   - 变更：`提案` / `已确认` / `进行中` / `已验证` / `已合入` / `已废弃`
5. **周节律**：每次会话结束前检查一次"三者是否一致"（README 清单 ↔ current 文件 ↔ PROGRESS 状态）。

## 5. 决策记录（ADR）何时写

出现以下任一情况必须写 `decisions/NNN-*.md`：
- 在两个及以上方案间做过取舍（如选型、存储结构、并发模型）；
- 改动会带来不可逆代价或迁移成本；
- 未来可能被质疑"当初为什么这么定"。

ADR 固定四段：**背景 / 比较过的方案（含代价）/ 决定 / 代价与后续**。被新 ADR 替代时状态改为 `已被 NNN 替代`，不删除。

## 6. 归档规则

- 已合入的变更目录整体移入 `archive/changes/`；被替代的规格移入 `archive/current/`。
- 归档文件正文不改，仅在头部补一行替代关系说明。
- ADR 不归档，永久保留。

## 7. 禁止事项

- 直接改 `current/` 而不留变更记录（纯 typo、注释、格式除外）。
- 只改代码、不改规格，导致规格与实现长期漂移。
- 在 `spec/` 根目录堆砌新的散装 `.md`（必须归入分组目录）。
- 删除历史文档或用新文档覆盖旧文档而不标明替代关系。
- 把"计划做"的事写进 `current/`（`current/` 只描述已验证的现状；计划放 `plans/`，进行中放 `changes/`）。
