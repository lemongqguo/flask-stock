### 1. Spec 怎样跟着产品一起变化

第一课用 Spec 把场景、功能和关键行为写清楚，帮助人和 Agent 对开发目标形成共同理解。到了持续维护阶段，这些内容仍然有用。

**SpecDD 的作用可以从两个阶段来看：**

- **开发之前**，明确使用场景、术语、边界和验收方式，减少理解或定义错误。例如“回答更好”需要说明好在哪里，“评论最热烈”需要明确观察什么。
- **持续维护时**，保存系统当前支持的能力、设计原因和已知限制，降低接手成本。新的开发者或 Agent 可以从规格入口了解情况，不必翻完之前所有聊天。

需求会变化，Spec 也会跟着修订。新要求先记录为待确认或待实现的变更，明确后推进开发；实现并验证以后，更新当前有效规格。旧决定保留变更原因和替代关系。

提前把约定写清楚，是为了让这次开发有依据；持续把约定维护好，是为了让后面的开发接得上。

#### 1.1 当前约定、变更过程与历史依据

如果每次修改都只新增一份文档，文件会越来越多，但“现在到底以哪份为准”仍然可能说不清楚。

接手时先找现有的规格入口，缺少时再补齐。一个小项目可以先把信息分成三类：

| 位置             | 主要内容                              | 什么时候更新         |
| ---------------- | ------------------------------------- | -------------------- |
| `spec/README.md` | 当前有效规格入口、状态、已知限制      | 有效约定或状态变化时 |
| 功能规格         | 当前场景、行为和验收条件              | 相关行为被确认修改时 |
| 变更记录         | 原因、旧约定→新约定、影响面、验证结果 | 一次变更推进过程中   |

重要设计选择还可以留下简短的决策记录（ADR）：当时遇到了什么问题，比较过哪些选择，为什么选这一种，有什么代价。以后换方案时注明替代关系，便于理解当初的决定。

#### 1.2 不同项目可以有不同的组织方式

这些信息可以用目录管理，也可以放在协作工作台里。观察几种做法，有助于理解它们各自在解决什么问题。

OpenSpec 将当前规格与进行中的变更分开组织。变更完成后，将差异合入当前规格，再保留历史，方便分别查找“系统现在是什么样”和“这次准备改哪里”。

Agently 的维护目录则按持续规则、计划、已实现功能的规格和归档组织，再用索引指向相关内容。目录帮助导航，适用版本、实现状态和验证范围仍写在正文里。

![Agently 的规格组织方式：目录职责示意](D:\BaiduNetdiskDownload\AI大模型应用第24期\22-持续迭代与安全重构\assets\02_规格组织.svg)

RioWork 将需求目标、任务、阶段成果和历史变更关联起来，方便接手者查看“要达成什么”“目前做到哪里”“依据在哪里”。

这些做法共同关心的是：当前状态容易找到，进行中的变化有记录，重要决定能够追溯。小项目用一个索引和几份规格，就可以开始维护；以后再根据协作需要调整组织方式。

#### 1.3 一次变更的维护过程

![一次变更从问题到当前状态](D:\BaiduNetdiskDownload\AI大模型应用第24期\22-持续迭代与安全重构\assets\03_变更闭环.svg)

先确认问题，再判断本轮属于哪种变化：实现没有满足原有约定，还是产品需要调整原有行为？前者可以依据现有规格补回归测试并修复；后者则先明确新的约定，再调整相应测试。

实施并验证以后，还要更新有效规格、当前入口和遗留问题。完成记录里既能看到结果，也能看到依据：为什么改，哪些测试保留，哪些期望被替代，实际验证到了什么范围。



## spec/ 规格文档目录

所有需求与设计以规格文档（spec）形式沉淀管理：

- 命名规范：`NNN-slug.md`，编号三位递增（如 `001-live-comment-assistant.md`）
- 每次需求变更、功能新增、技术方案调整，均新增一份 spec 文档，历史版本保留不删
