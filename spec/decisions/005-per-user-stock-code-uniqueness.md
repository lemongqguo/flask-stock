# ADR-005：同一股票代码按「归属人唯一」，并配套监控请求去重

**状态**：已接受　|　**日期**：2026-10-26
**关联规格**：[002 股票订单管理](../current/002-stock-order.md)、[004 后台监控服务](../current/004-monitor-service.md)、
[001 用户认证](../current/001-user-auth.md)
**关联变更**：[2026-10-26 多用户数据隔离](../archive/changes/2026-10-26-multi-user-ownership.md)

## 背景

引入订单归属（`stock_master.user_id`）后，`stock_code` 原本的**全局唯一**立刻变成一个产品问题：
两个人能不能各持有一条 `SZ002027`？

这不是技术细节，而是三种截然不同的产品形态，且三者的数据模型改动互相排斥，
**必须先选型再开发**（评估过程见 `design-preview/多用户数据隔离-需求评估.md` §3.2）。

## 决策

采用**方案 A（按人唯一）**：

- 唯一键由 `UNIQUE(stock_code)` 改为 `UNIQUE KEY uk_user_code (user_id, stock_code)`；
- `stock_code` 保留非唯一索引供搜索，不再约束跨用户重复；
- 每个人拿到独立的阈值（`stock_warehouse` / `stock_pe` / `stock_pb`）、独立的告警、独立的 K 线与 AI 报告；
- **强制配套**：`StockMonitor` 每轮按 `stock_code` 共享行情快照与日线结果，
  同一代码一轮只打一次雪球请求，避免外部请求量随用户数线性增长。

次要决策：

1. 去重放在**取数环节**（`check_and_alert` / `_sync_kline` 调 `_shared_result`），而不是在派活前按代码分组去重行——
   后者会让"多出来的那些行"拿不到自己的行情回写，等于用牺牲正确性换请求数；
2. **失败不缓存**，且每轮开始清空缓存：跨轮复用会拿昨天的价格判今天的告警；
3. 等待者（第二个同代码任务）阻塞复用而非各自重取，用的依然是同一个线程池，不额外占资源。

## 代价

- **行情 / K 线 / 指标快照会按人重复落库**：同一只票 5 个人盯着就有 5 份 `stock_kline`。
  换来的是阈值与告警互不干扰，认为值得；真到数据量大时可另立变更做"共享行情 + 私有阈值"的拆分。
- **去重引入少量并发复杂度**：`_shared_result` 用 `threading.Event` 做"首个请求者 / 等待者"划分。
  若首个请求失败，同代码的其他订单本轮也会拿不到数据（相当于单点失败被放大一轮）——
  考虑到同一代码的请求要么都成功要么都失败，判定可接受。
- **等待者会阻塞一个线程槽**直到首个请求走完（含 30~300s 节流 sleep）。
  默认为此付出的代价 ≤ 省下的那次外部请求，但若将来同一代码被几十人持有，需要重新评估线程池大小。

## 被否决的方案

- **方案 B（共享标的 + `stock_watch` 关联表）**：行情只采一份看似最优，但阈值 / 告警 / 备注随之变成**共享**状态，
  A 改阈值 B 跟着变，与「只看到自己名下」的直觉直接冲突；且几乎每个查询都要多一层 JOIN，改动面最大。
- **方案 C（全局唯一 + 单一 owner）**：最省事，但多人想盯同一只票时直接不可用，
  还会冒出「要不要告诉用户被谁占用了」的隐私问题。
- **不改唯一键**：加完 `user_id` 却保留全局唯一，等价于方案 C，且会通过数据库隐式表达一个没人讨论过的产品规则。
